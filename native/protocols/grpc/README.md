# Native Tonic adapter and bounded ownership

This B18 leaf uses Tonic 0.14.9's public `Codec`, `Encoder`, `Decoder`, `Grpc`, and four service traits over `Bytes`. B17 supplies its existing HTTP/2, rustls, route admission, Tokio runtime, callback scheduler, diagnostics and shutdown. The source-linked `host.rs` and `exports.rs` compose into that Host; the exact original 48 Server exports and Core create/start/take/retire protocol remain unchanged. The native leaf introduces no executor, listener, managed transport, private Tonic API, or new ABI.

The authoritative design is NativeWeave-Design commit `c62cdb8aee833b6ab1a03e29a3f59f81a1b483f9`, `docs/api/server.md` sections 7 and 10 and `docs/server/protocols-and-observability.md` section 2. This proof applies to the pinned Linux x64 source and identity-compression profile. `codec-sources.json` records the exact upstream file hashes and commit URLs used below. A changed dependency, feature or allocation path requires rechecking this proof.

## Message and codec capacity

Let `E` be the method's positive maximum encoded payload bytes, `C` the Host's positive maximum chunk bytes, and `H = min(MaxHeaderBytes, 32768)`. Every admitted call grants the following codec capacity before Tonic constructs its buffers:

| Controlled native allocation | Grant before allocation | Owner and release boundary |
| --- | --- | --- |
| Tonic receive scratch | `E + 2*C + 5` | Shared codec grant; destroyed after the complete incoming Tonic stream |
| Tonic encode scratch | `E + 5` | Same grant; destroyed after the complete outgoing Tonic Body |
| One decoded message of length `L` | `max(1,L)` | Exact `Box<[u8]>` behind `Bytes::from_owner`; all clones/nonempty slices retain its grant |
| Reserved outbound message capacity `R` | `R + 5` | Queue permit and grant transfer together; native message Box, then framed Box, use the same grant in sequence |

`RawCodec::new` acquires the combined `2*E + 2*C + 10` grant atomically from B16's native global/request coordinator. There is no payload waiter or implicit retry. Tonic's public `BufferSettings` selects these initial capacities. Compression stays disabled, so its compression buffers allocate no payload.

Tonic `decode.rs` initially allocates one `BytesMut` of the selected receive capacity. `ChunkBody` passes at most `C` bytes per poll without interpreting gRPC framing. In `ReadHeader`, the unread suffix comes from at most one delivered chunk; after consuming the five-byte prefix, Tonic calls `reserve(declared_length)`. The declared length has already passed `E`. If the consumed prefix is smaller than the unread suffix, both are bounded by the delivered chunk, and `E + 2*C + 5` suffices without growth. If the prefix is larger, Bytes 1.12.1's unique Vec path reclaims it when needed. During `ReadBody`, the preallocated extent also covers the incomplete message plus one next chunk. Our decoder uses `copy_to_slice`, never `split_to`/`freeze`, so no receive-scratch alias escapes and prevents reclamation. The descriptor gives each concrete decoder a fresh unary allowance; a second complete unary/server-streaming message fails with status 3 before managed dispatch. Client/bidi decoders maintain independent cumulative quotas.

Tonic `encode.rs` reserves five prefix bytes and calls the public encoder. The eager `E + 5` capacity covers the complete message. Yield threshold 1 forces one message per returned frame, including an empty protobuf message. `CreditedBody` copies that complete Tonic frame into its own exact Box and drops the Tonic frame before another poll. Consequently the next encode has the unique backing required by Bytes' reclaim path; no uncredited Tonic-buffer alias reaches Hyper or a caller.

The outbound queue contains at most one message. Waiting for its permit acquires no new payload credit. After the permit is available, `Call::reserve` tries `R + 5` once; quota failure drops the permit immediately. The synchronous ABI `grpc_write_create` copies caller bytes only after the token, request and operation slot are validated. Its native message Box has actual length at most `R`. Tonic copies it into the separately granted encode scratch and drops that Box; the same `R + 5` owner then covers the independently escaping framed Box. At conversion overlap, the scratch and final frame remain separately charged. A never-started operation drops the copied message, permit and grant without running work.

Field destructor order is part of the proof. Pinned Tonic drops `Streaming.decoder` before `Streaming.inner`, and `EncodedBytes.encoder` before its `BytesMut` fields. The input `StreamInput` and output `CreditedBody` therefore hold an additional Arc of the same grant **after** their Tonic payload field. This delays final credit release until the entire inner object is destroyed; it does not reserve a second capacity. Exact Box owners declare storage before credit for the same reason.

The Host rejects a route when its unconditional floor cannot fit either native quota:

`2*E + 2*C + 10 + 2*H + 200*48 + 2048`.

The calculation is checked. Conditional binary scratch, messages, and output metadata remain runtime nonwaiting grants. This startup check does not require all optional simultaneous outputs to fit. Transport/TLS buffers and fixed admitted operation/control records are separately bounded by B17; these counters do not claim whole-process RSS or allocator bookkeeping.

## Metadata bounds and escaping owners

HTTP wire text and decoded gRPC metadata have separate immutable blocks under one request metadata owner. Before either block is constructed, `project_metadata` checks the entire split count, wire size and decoded upper bound. Its stack array has 200 borrowed segment descriptors, each covered by an explicit 48-byte allowance with a compile-time size assertion. A field containing many commas cannot evade the count cap. Empty segments remain real entries; only surrounding SP/HTAB are trimmed.

For largest encoded binary segment `S`, the request projection grants `2*H + 200*48 + 2048 + 3*S`. The first two terms cover both bounded blocks and all segment descriptors. `3*S` covers the segment's HeaderValue backing, Tonic's decoded temporary and copy overlap; 2048 bounds the single temporary map/control storage. Before the next segment, that temporary is dropped. The sibling ordinary HTTP block uses an exact-size preflight allocation rather than geometric Vec growth. The decoded Vec has fixed capacity `H` and checks each appended entry. Invalid alphabet, padding, count, byte bounds, decode failure or denied scratch credit destroys unpublished owners and never invokes managed business work.

Each admitted binary segment is inserted as original wire text through `HeaderValue`, wrapped by public `MetadataMap::from_headers`, and decoded by public `get_bin(...).to_bytes()` once. We do not pass base64 wire text to `MetadataValue::from_bytes`. The adapter additionally rejects malformed partial/interior padding because the pinned Tonic decoder accepts padding forms outside this strict profile. Per-name repeated order is preserved. Outgoing binary metadata is raw bytes and uses public `MetadataValue::from_bytes`, leaving wire encoding to Tonic.

Response metadata grants `8*block_bytes + 4096*entry_count + 16*detail_bytes + 1024` before construction. The source multiplier covers binary encoding and immutable-value overlap; the per-entry allowance covers bounded map tables, cloned Status/header projections and owner wrappers. Pinned http's collision path can double indices while `5*entry_count >= raw_capacity`; after that it changes the hash function, giving fewer than ten index slots per distinct entry (plus its fixed minimum). Buckets fit 128 bytes, extra-value nodes fit 96, and index slots use four. Source maps, Status clones, conversion temporaries, and the destination map contribute at most five simultaneous projections; Vec clone capacity follows length, while destination growth's old/new overlap is covered. The 4096-byte allowance per source entry plus the fixed minimum covers this peak, including retained value wrappers. Compile-time assertions bind the public component sizes used by that bound.

The detail allowance covers the finite UTF-8 copy, Status copies and percent-encoding overlap. Each UTF-8 byte expands to at most three ASCII bytes; pinned percent-encoding builds a String, whose Rust Vec growth can retain an old allocation below `3*d` while the new capacity is below `6*d`. The subsequent exact Bytes copy is at most `3*d`; these phases plus the bounded Status string copies fit `16*d + 1024`. An encoded visible-length-only reservation would not cover this overlap. The fixed allowance covers protocol-generated fields and empty batches. All operations are checked and nonwaiting; the source block itself is capped at `H` and 200 entries. Control-map allocation is conservative, not inferred from payload visible length.

Headers and trailers may survive the Body that produced them. `retain_headers` adopts each validated HeaderValue into an owner-backed Bytes value holding an Arc to the whole batch grant. `http` 1.5.0's public `from_maybe_shared` adopts that Bytes without copying its payload. Hyper/HeaderMap clones therefore keep the whole grant until the last value owner disappears, even after returning a trailers frame, ending the body, or completing dispatch. Dropping Call metadata alone cannot release an escaping trailer's grant.

The request's immutable header projection is an intentional retirement anchor. The Host removes a retired request with this final anchor only when body completion, dispatch retirement and operation retirement are established, managed bytes are zero, native bytes equal exactly that anchor, the metadata credit is unshared, and the request Head Arc has no external owner. Retained metadata handles, header values, message buffers or other credits keep the request pending. This is not a general exception for retained payloads.

## Cancellation, status and retirement

All operations use existing Core result kinds and the Server's bounded scheduler. Read returns a complete-message buffer owner (including zero length) or an owner-free EOF. One read and one write may be pending independently. Raw HTTP reads and all raw response create paths reject a gRPC request before operation creation or response mutation.

Core asks for cancellation during normal successful operation cleanup. A completed or retired read therefore does not stop the input stream. A genuinely pending read may latch input stop. Deterministic early inbound disposal uses an existing Created read: call `operation_request_cancel` before `operation_start`, then start with an uncanceled managed token and join terminal plus retirement. The sticky input stop precedes any ready-message race and does not cancel the output direction. Common dispatch completion still retires unread native input.

The strict native timeout accepts one 1–8-digit ASCII number and `H/M/S/m/u/n`, caps it against the route timeout before checked monotonic addition, and persists across response headers and body lifetime. A pending call emits status 4 at expiry. A previously committed success/error remains the winner: terminal admission first owns its queue slot and has no subsequent wait before publication. Both pre-response scheduling and Body polling preserve this earlier terminal. Cancellation intent never means a remote side effect was rolled back or that a peer consumed a frame.

A peer can reset HTTP/2 before a response Body is constructed. `PendingResponse` retains the request over this response-future interval. On future drop it records cancellation, retires unread input, ends body ownership, and retires an undispatched ticket; on success it transfers that obligation to `GrpcBody`. Pinned Tonic may report a reset input as EOF before cancellation wins. The whole-call cancellation latch still becomes observable, but an already successful EOF is not retroactively relabeled.

Native operation completion, managed task completion, request dispatch completion, Body destruction, buffer-owner destruction and Host shutdown are separate boundaries. Tests inspect both the exact Core retirement gate and final request/global counters. No callback/root or service scope is released based only on response headers or a successful message write.
